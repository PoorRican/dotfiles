# Small-node fit

- Establish the live workload, image identities, dependencies and placement rather than assuming architecture notes reflect the current deployment. Compare simultaneous pod usage and growth over representative history, including workload peaks and restarts.
- Inspect current pods and controller types, image IDs, resource limits, host paths and service dependencies. Filter container names explicitly in historical queries: an unrestricted namespace with short-lived jobs can return thousands of series.
- For the simultaneous pod maximum, adapt the selector in this template: `max_over_time((sum by (pod) (container_memory_working_set_bytes{namespace="<namespace>",container!="",container!="POD"}))[30d:1m])`. Inspect per-container current, median and peak values separately, and bucket range-query samples by day to expose uptime growth.
- RSS and working set are different measurements; their similarity alone cannot establish anonymous-heap or page-cache composition. Check the relevant memory breakdown when that distinction matters.
- Measure CPU at a resolution appropriate to burst sensitivity; longer rate windows can hide short spikes. Include measured agent, networking and monitoring overhead on the target node class, not just application containers.
- Estimate write volume from workload and device counters and compare with the specific storage device's endurance and workload. Network dependencies can block placement even when memory fits; test required service reachability from the target node.
- Cross-check write-rate estimates with `node_disk_written_bytes_total` for the relevant device, then inspect the host path to attribute the writer. Check whether networking agents and service routing are required on the target, not just application memory.
- Inspect the registry image index and platform-specific manifests for the target architecture. An image tag or Dockerfile alone does not prove the deployed digest supports that architecture.
- Report measured usage, target overhead and constraints separately from estimates. A timed-out recursive size scan is incomplete evidence, not zero usage; bound costly scans.
- For an authorized long copy, track process identity and output before starting. A client timeout does not prove a remote copy stopped; inspect identity and arguments before retrying. A failed unprivileged `kill -0` can mean lack of permission rather than termination.
