# Capabilities and enforcement

## Enforcement and signed capabilities

- A schema declaration does not show where invalid input is rejected or who can bypass it. Exercise a violating input at the relevant runtime boundary and identify the enforcement layer.
- A client sending a conditional header proves cooperative behavior, not that the capability binds that header. Inspect signed headers and test the same capability without the condition; tampered-signature rejection proves signature validation, not that a particular condition is bound.
- Use an independent reference derivation for signing tests: expected values generated by the implementation can repeat its canonicalization error. Distinguish expiry, tampering and authorization failures; an error is not evidence of absence.

## Offline admission-policy verification

- Render the overlay, extract `spec.variables` and `spec.validations`, compact expression whitespace (`" ".join(expr.split())`), and compare both lists with a reviewed golden JSON. This detects changes to rendered text; it does not execute CEL or establish that the reviewed artifact is deployed.
- Generate positive fixtures from the real submission renderer and add other valid cases where needed. Regenerate into a temporary directory and compare with committed fixtures to detect renderer drift.
- Independently re-encode policy intent as an evaluator of the object, resource and username returning violated messages. Use the policy's verbatim messages; positives should return no violations, and deterministic single-rule hostile mutations should return the expected message. This tests the reimplementation, not the actual CEL.
- Have an independent reviewer reconcile CEL logic rule by rule with the evaluator, contract and rendered manifests, including negative cases and expressions that could error on the API server. Label offline results accordingly.
- Check missing map keys and optional fields before indexing, and make conditional quantity ceilings total for unknown labels or hosts. An expression error under `failurePolicy: Fail` is handled through the binding's validation actions; it is not necessarily a denial if the binding only warns or audits.
- When `DefaultTolerationSeconds` is enabled, Pod admission may add not-ready and unreachable `NoExecute` tolerations before validation. A toleration allowlist for Pods must account for applicable defaults; a Job template is not the subsequently created Pod.
- Where possible, confirm positive and negative cases against the target API server with the actual policy, binding, parameters, matching scope and mutation behavior. Server dry-run of a Job does not itself create its controller's Pod, so test the Pod admission path separately when that behavior matters.
