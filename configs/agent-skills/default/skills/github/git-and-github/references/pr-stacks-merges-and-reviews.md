# PR stacks, merges and reviews

Scope: Branch topology, merge policy, overlap cost and combined-state validation.

## Stack shape and merge policy

- A stacked PR series has each PR based on the preceding branch, with the chain created bottom-up. Touching related files is not itself a dependency when a change does not need the earlier branch's code. (src: stacked-prs, 2026-05-04; stacked-independent-fix-set-landing, 2026-08-18)
- GitHub does not necessarily retarget a stacked PR after its base merges. A higher PR left on a lower branch can merge successfully into that literal base without putting its change on the main branch. (src: github-linear-stack-merge-cascade, 2026-09-04)
- Merge strategy depends on repository policy and desired history: in some linear stacks, merge commits preserve stack history and avoid a post-merge rebase cascade; squash and rebase strategies have different history and retargeting consequences. No strategy is universal. (src: github-linear-stack-merge-cascade, 2026-09-04; land-commits-and-capture-image-digest, 2026-08-23)
- Stacked-PR descriptions are clearest when they describe delivered state rather than internal commit history or identifiers. (src: stacked-prs, 2026-05-04)
- A conflict-resolution change to a lower branch may require propagation through downstream branches and renewed mergeability checks. Before branch pruning, equality between remote main's tree and the recorded original stack-tip tree is landing evidence. (src: stacked-prs, 2026-05-04; github-linear-stack-merge-cascade, 2026-09-04)
- Independent sub-fixes of one issue are separate PRs that each branch from the base, not from a sibling's unmerged branch. Branch from the base (`git worktree add -b <new> <path> origin/<base>`, or in a checkout you own stash, switch, branch, pop), confirm the base with `git merge-base`, and judge CI by the PR-event run. (src: independent-fix-landing lesson, 2026-11-08)
- `gh pr merge --delete-branch` has been seen to fail its local branch deletion (for example when the base branch is checked out in another worktree) while the remote merge succeeded. Re-read the PR state (`gh pr view <n> --json state,mergedAt`) before retrying, because the remote may already be MERGED; behavior was not re-run in the audit. Retarget PRs based on a branch before deleting it, and read back each one's base. (src: gh-merge-delete-branch lesson, 2026-11-08)
- Read the actual PR base, not the PR body or an assumption that it targets the default branch. A clean mergeability badge against an abandoned stack base (a closed, unmerged PR) can hide obsolete ancestor changes in the comparison with the default branch. (src: open-PR relevance audit lesson, 2026-11-08)
- `--match-head-commit` protects the PR head, not the base tree: concurrent PRs can land in between, so a PR that owned 3 files can produce a merge commit with 64 changed paths. Before qualifying or deploying a build from a merge commit, inspect the merged-tree delta against the previously qualified commit (`git diff --stat <qualified> <merge>`) instead of the PR's file list, and check deployment ordering prerequisites such as a schema migration that must precede the image needing it. See [landing-proof.md](landing-proof.md) for the pinned-head procedure. (src: merge-commit-qualification lesson, 2026-11-08)
- To split an open PR that bundles an unreviewed prerequisite range without rewriting history: `git fetch --prune origin`, verify the prerequisite commits are absent from the target, publish a new branch at the prerequisite tip, open a base PR from it, retarget the downstream PR to that branch, rewrite both titles and bodies, and verify ancestry, file scope, bases and mergeability. (src: bundled-prerequisite-split lesson, 2026-11-08)

## Overlapping changes and CI

- Merge order can account for predicted file overlap: stacked bases come first, then lower-overlap PRs, with the heaviest-overlap PR last when that reduces repeated conflict work. (src: overlapping-pr-fan-merge, 2026-08-19)
- Union-merging additive conflict sides can break syntax when a shared closing delimiter sits after the conflict block. The text following the markers is part of the construct; green CI on each PR separately does not validate the conflict-resolved combination. (src: overlapping-pr-fan-merge, 2026-08-19)
- Opening a PR can cancel a push-triggered CI run for the same SHA when repository concurrency settings replace push runs with PR-event runs; that cancellation alone is not evidence of code failure. (src: stacked-independent-fix-set-landing, 2026-08-18)

## Splitting a dirty tree into a stack

- Ground first: `git status --short`, `git diff --stat`, `git log --oneline --decorate -n 20`, `git worktree list`. Group changes by dependency order, not folder count: plumbing, schema and foundational refactors, then behavior, then docs and tooling. Exclude scratch files, secrets and local probes unless asked. (src: split-stacked-changes, 2026-11-08)
- Snapshot the full unsplit tree on a local-only checkpoint branch that serves only as a restore source, and only in a worktree you own. In a shared checkout never sweep other actors' dirty files into a snapshot commit (see [shared-checkouts-and-recovery.md](shared-checkouts-and-recovery.md)).
- Build bottom-up, each branch from the previous one (`git worktree add -b <new> <path> <previous>`), restoring only the relevant paths with `git restore --source <snapshot> -- <paths>`. Split a mixed file by constructing each layer's blob ([isolated-index-commit.md](isolated-index-commit.md)) rather than interactive `add -p`. Use one to three conventional commits per branch and keep each branch clean before creating the next.
- Verify each layer with the narrowest meaningful tests. Branch-local failures that only reflect missing higher layers are expected; run full verification on the top branch. Repair wrong ancestry one branch at a time, bottom-up, with `git rebase --onto <new-base> <old-base>` (only for your own unpublished branches, see [branch-history-and-landing.md](branch-history-and-landing.md)), recheck with `git merge-base --is-ancestor <lower> <upper>`, and rerun the targeted checks after rebasing.
- To continue a numbered series, a base named `<prefix>/NN-slug` yields `<prefix>/NN+1-...`, where the next number is the maximum over local and remote refs (`git for-each-ref --format='%(refname:short)' refs/heads refs/remotes`) plus one; otherwise keep the repository's prefix, and follow a stronger repository convention when one exists.
- Report the branch order lowest to highest, the commits per branch, the excluded files, and the PR chain: each branch targets the previous one and the bottom targets the original base.

## Sweeping review comments across a stack

- Collect raw PR metadata with `gh` or GraphQL first (`gh pr list --state open --json number,title,headRefName,baseRefName,url,reviews,comments`, then each PR's review threads); a bot's review summary is not a finding. Classify every comment as actionable, already fixed in a later branch, obsolete or blocked, and return comment-to-status, files and tests per pass. (src: stacked-pr-comment-sweep, 2026-11-08)
- Fix on one integration branch off the current tip, grouped by concern (dependency pin, runtime, sync, telemetry, formatting-only last) so each commit stays bisectable.
- Before history surgery run `git status --short` and checkpoint unrelated tracked and untracked work: ignored files do not enter a normal stash, so note them separately, and in a shared checkout never stash another actor's edits. Split a too-large unpublished top commit with `git reset --soft HEAD~1` and path-scoped commits. Rewriting a branch that is already pushed follows [branch-history-and-landing.md](branch-history-and-landing.md); after any approved push that rewrites a remote branch, read back `git log --oneline --decorate`, `git status --short --branch` and the PR head.
- Report the new commit breakdown, comments addressed versus blocked, tests run, the push confirmation and the unrelated files left preserved.
