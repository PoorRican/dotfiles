# GitHub API reviews and issues

Scope: Distinct GitHub issue, conversation, formal-review and inline-thread surfaces.

## Comments, reviews and threads

- PR conversation comments, formal reviews and inline review threads are separate GitHub surfaces. `gh pr view --json comments` does not report review-thread resolution or outdated state. (src: github-open-pr-feedback-audit, 2026-07-26; github-code-review, 1969-12-31)
- Inline review comments anchor to the PR head commit; `line` refers to the new file version, while a comment on a deleted line uses `side: LEFT`. Multiple inline comments can be submitted in one atomic review request. (src: github-code-review, 1969-12-31)
- A visible inline comment is not automatically outstanding: unresolved-current threads, unresolved-outdated threads, resolved threads, formal reviews and top-level conversation comments are distinct states or surfaces. (src: github-open-pr-feedback-audit, 2026-07-26)
- Broadly nested GraphQL traversals can fail with `MAX_NODE_LIMIT_EXCEEDED`; modest per-connection bounds reduce the chance of an unnecessarily large nested result. (src: github-open-pr-feedback-audit, 2026-07-26)
- A GraphQL review-thread ID and a REST root-comment database ID are different identifiers. A descendant supersedes feedback only when its code concretely fixes the behavior or removes the criticized path; a resolution reply should cite that descendant evidence. (src: github-stacked-review-relevance-resolution, 2026-07-29)
- Review-thread relevance is judged against both the revision the reviewer saw and the current stack tip; descendant code may supersede an issue without erasing whether the original report was valid. (src: github-stacked-review-relevance-resolution, 2026-07-29)
- PR conversation comments retrieved with `gh pr view --json comments` differ from a known inline comment retrieved through the pull-request review-comments API. (src: get-pr-comments, 2026-06-19)
- For follow-up fix PRs, reply to each review thread with a link to the fix as soon as it exists and resolve the thread only after the follow-up PR merges. A report cited from a review belongs in a tracked, dated document, not a scratch path. (src: review-thread-hygiene lesson, 2026-11-08)
- A fresh read of a PR diff after a push can return the pre-push diff (observed 2026-10-07; cause unestablished). Bind the review to explicit base and head SHAs and an exact committed diff, merge with `gh pr merge <n> --merge --match-head-commit <reviewed sha>`, then verify the merged state and the two parents. (src: pr-diff-staleness lesson, 2026-10-07)
- An observational status request calls for reading and reporting feedback and checks, not requesting a review or editing. For a configured independent-review gate, check the current head for an existing running or completed review before requesting another; bind a completed verdict to the exact head and reviewer. An acknowledgement, old-head verdict, self-authored reply, local inspection, passing tests or resolved threads is not an independent review. Repeat the gate after a head change. Where policy permits an owner waiver, record and read it back for the unchanged head and diff; it does not waive required checks or protections.
- Use the repository-configured review trigger and serialize the pushed SHA in its request; read back the request and distinguish pending from completed. Recheck reviewer availability for this PR, rather than treating an error on another PR as a current block.
- Collect head, base, mergeability, reviews, conversation and inline comments, threads and checks. Paginate threads and their nested comments independently and compare enumerated counts with totals. For REST aggregation, `gh api --paginate --slurp ENDPOINT | jq ...` wraps pages before filtering; retain `pipefail`. Check for an existing reply before retrying an uncertain POST; read back the reply ID and `in_reply_to_id`. Resolve only under repository policy after a verified published fix, then read back each thread and check for new findings.

## Issues and checks

- GitHub's `/issues` list endpoint also returns pull requests; results need to be filtered for entries containing `pull_request` before they are treated as issues. (src: github-issues, 1969-12-31)
- `Closes #N`, `Fixes #N` and `Resolves #N` in a PR body link an issue for automatic closure when the PR merges. (src: github-issues, 1969-12-31)
- Commit statuses and Actions check-runs are distinct surfaces; either alone may not explain a PR's complete CI state. (src: github-pr-workflow, 1969-12-31)
- GitHub's REST API supports direct PR merge, while enabling auto-merge uses GraphQL. (src: github-pr-workflow, 1969-12-31)
- An Actions job can conclude failure while its failing step is cancelled, so `gh run view --log-failed` may exit 0 with no log. Inspect the step conclusions, fetch the job logs through `gh api` (add `--allow-escape-sequences`), and rerun only after attributing the interruption, never to erase an assertion failure. (src: ci-cancelled-step lesson, 2026-10-03)
- Attribute a failed job to its phase and full error context before changing code: installation, fixture startup, assertions, runner interruption and image build are different failures. An interruption before tests is not an assertion failure. If retry is authorized, first ensure no attempt is running, retry failed jobs once and read back status and attempt; queued is not passed. For an isolated fixture-startup failure, rerun affected tests unchanged and, if they pass, retry the required full hook; investigate repetition rather than bypassing the gate.
- A full-project type check discovering zero files is not green. Read configured includes and exclusions; only if they cover all tracked Python and notebook files, enumerate them NUL-safely, assert nonempty and pass them to the checker with its original exclusions reapplied. Check independently configured workspace trees separately and retain analyzed-module and error counts; positional-file mode may ignore configured exclusions. (not re-run)
- An issue whose acceptance criteria reference live state (data population, null rates, a running system) must not close on code, schema and migration evidence alone: gate closure on a read-only check of that state, or leave the issue open and name the check. Schema-only issues may close from static evidence. Re-verify a delegate's claim that a test was removed before relying on it. (src: issue-closure lesson, 2026-11-08)
